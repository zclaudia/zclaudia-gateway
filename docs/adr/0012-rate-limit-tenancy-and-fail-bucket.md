# 0012. 限流：合法请求按租户计额，未认证失败按 IP 单桶

- 状态：Accepted
- 日期：2026-10-16

## 背景

网关有两套固定窗口限流：已认证代理请求（原 200 次/min/客户端 IP）与未认证失败（10 次/min/客户端 IP）。两处都在生产中暴露了模型问题。

按 IP 给**已认证**流量计额在两个方向上都不成立。同一个 NAT/CGNAT/办公出口后的多台设备共享一个桶，互相挤兑——移动端内嵌研究台一次页面导航约 15 个请求加 ~0.5Hz 轮询，几次导航就能把 200 撞满，而此时被限掉的是同一个用户的其它设备或同事；反方向看，一张凭证只要轮换源 IP 就能拿到 N 倍额度，而滥用凭证的一方恰恰是限流真正要拦的对象。若再加上反代：`req.ip` 在没配置 Express `trust proxy` 时恒为反代自身地址，全部客户端退化成一个桶（WS 侧因为走自己的 `extractIp` 反而不受影响）。

失败桶的问题在执行面而非数值面：只有代理与 `POST /api/backend/token` 两条路由记失败，`requireGatewayAuth`（`/api/discovery/backends`、`/api/notifications/*`）与 `requireRecoveryToken`（`/sync/registry`）直接返回 401 不计数，WS 握手密钥错误也只写审计不计数。攻击者只要换到这些路由，或改用"连上→发错密钥→断开"的 WS 循环，就绕过了本该最严格的那道限流。

安全前提：签发的凭证（`zgd_`/`zgb_`/`zga_`）是唯一认证；`resolveToken` 对**过期**与**伪造**的 token 都返回 null，两者走同一条错误路径，因此默认无法区分"攻击探测"与"诚实但过期"。

## 候选方案

1. **保持按 IP，只调大数字**：改动最小，立刻缓解误伤。但按 IP 的两个方向性错误都还在：NAT 后仍互相挤兑，凭证滥用仍可换 IP 放大。否决为唯一手段，保留为可选兜底。
2. **已认证按凭证（租户）计额，未认证按 IP 单桶（选定）**：限流的语义单位与真实的配额单位对齐——租户的设备共享额度的同时也只消耗自己的额度；未认证没有身份可归属，IP 是唯一可用的键，且此时严格是正当的。
3. **按 (凭证, IP) 复合键**：能同时约束"一张凭证一个来源"。但同一租户的多台设备各占一份额度，租户总量不可控——而租户总量才是要守的量。否决。
4. **用在途并发数替代速率**：对后端负载的约束更准，也不惩罚"一串快而小"的请求。但需要与代理的流式响应生命周期耦合，且抑制不了轻量滥用。留作后续可选项（[ADR-0003](0003-channel-transport.md) 的 channel 侧已有 `maxChannelsPerPeer` 与 per-channel 字节速率同形）。

## 决策

采用方案 2。

- 已认证代理请求的额度按 `credentialId` 计（`proxyRateLimit`，默认 1200/min）。可选 `proxyIpRateLimit` 作为"单一来源持有大量凭证"的粗兜底，默认关闭：它不是正常用量的限制器，而"一个来源持有很多凭证"更应该靠吊销凭证解决，开启反而有误伤整个共享出口的余地；确需开启时取租户额度的 3–5 倍。
- 数值取 1200（20 req/s）而非更紧的值：改成租户维度后，误伤的代价是真人正在使用时看到 429，而它要拦的另一种情况是失控客户端——无退避的重试循环一分钟是几千次，1200 拦得住，收紧到 600 拦不住额外的东西。诚实的重负载（agent 式工具调用、多设备同时操作）可能落在 300–900/min，因此 1200 留出 2–4× 余量，600 只有 1–2×。前提是客户端按 `Retry-After` 退避，否则 429 对用户可见——这一点网关无法保证，故默认值宁可放宽。
- 未认证失败统一经 `denyUnauthorized` / `recordAuthFailure` 记账（`authFailRateLimit`，默认 10/min/IP）。HTTP 各路由的 401 与 WS 握手的密钥拒绝共用一个桶；额度耗尽时一律 429（WS 上是 `gateway_error` 的 `RATE_LIMITED`），并带 `Retry-After`（固定窗口剩余秒数）。失败额度取偏严格的 10：凭证是 256 位随机串，10 与 30 对暴力破解的可行性没有区别，这个数实际是资源保护与"让探测付出代价"，而非密码学需要；而它偏严格是安全的，因为失败桶只统计失败尝试——用有效凭证换发新 token（`POST /api/backend/token`）不经过这个桶，误伤的客户端换发后立即恢复，不必等窗口结束。
- 桶的键统一由 XFF 感知的 `extractIp` 提供，HTTP 与 WS 一致；`GATEWAY_TRUST_PROXY` 的既有前提不变（仅置于会覆写该头的反代之后）。
- 窗口仍为固定 60s。过期与伪造的 token 计入同一个失败桶，不区分：共享出口的部署用 `GATEWAY_AUTH_FAIL_RATE_LIMIT` 调整额度。
- `MAX_WS_CONNECTIONS_PER_IP`（10）与 channel 配额不变：它们约束的不是速率。

## 后果

- 正面：正常用量不再被陌生邻居挤兑；租户用量可控、可解释，且不因换 IP 被放大；探测者无法靠换路由逃逸；反代部署下限流粒度回到真实客户端。
- 负面/需要承担的：过期的诚实凭证与攻击探测同池，NAT 后多台设备同时用失效 token 重试会一起收到 429（但恢复路径不受影响：`POST /api/backend/token` 用有效的注册凭证认证，只要成功就不进失败桶，因此换发新凭证后一切照常，无需等窗口结束）；固定窗口在边界处允许 2× 突发；计数仍在进程内存里，多实例部署各自计数，且各桶随不同键无界增长（依赖 5 分钟清理周期，无上限保护）。
- 触发重新评估的条件：共享出口下多台设备同时持失效凭证、互相挤占失败额度并影响彼此的重试；或需要按租户做配额与计费——届时需要持久化计数、滑动窗口或令牌桶。
