# 0011. 后端访问凭证原地轮换：每个注册凭证只有一行

- 状态：Accepted
- 日期：2026-10-14

## 背景

后端用 `zgb_` 注册凭证经 `POST /api/backend/token` 换发短期 `zga_` 访问凭证（[ADR-0002](0002-identity-issuance.md)）。此前每次换发都新建一条凭证记录：SDK 在每次建连（含每次断线重试、每次进程重启）都换发，旧记录过期后也不会消失，管理列表里很快堆满同名的 `access:<父凭证名>`。

SDK 侧已改为在同一进程内缓存未过期的访问凭证，但进程重启仍会换发；换发时清理过期行只能把增长控制在"一个 TTL 内的重启次数"。运营者要的是"每个后端永远只有一行访问凭证"。

安全前提不变：服务端只存 token 摘要；每次换发必须返回新的 secret，不能延长旧 secret 的寿命——否则泄露的访问凭证只要被持续续期就永远有效，短期票据失去意义。

## 候选方案

1. **每次换发新建一行，换发时清理同父凭证下已过期的行**：保留按单张 token 的审计与吊销；行数有上界但不恒定（≈ TTL 内的换发次数）。
2. **延长旧 token 的有效期（滑动续期）**：服务端只有摘要，拿不到旧明文返还给调用方；若改为"持旧 token 续期"，泄露的 token 可被无限续期。否决。
3. **原地轮换（选定）**：每个注册凭证至多一行访问凭证；换发时在同一行写入新 secret 的摘要并重置有效期，旧 secret 立即失效。

## 决策

采用方案 3。

- 换发：若该注册凭证已有访问凭证行，则在同一行轮换——新 secret、新摘要、`expiresAt` 重置为换发时刻起算、`createdAt` 更新为本次换发时刻（即"当前 secret 的签发时间"），并刷新名称与 `backendId`；没有则新建。凭证 id 保持不变，在线连接与审计引用的 id 稳定。
- 轮换会清除该行的 `revokedAt`：单独吊销访问凭证的目的是作废当时的 secret，轮换后它已作废；要阻止后端再换发，应吊销注册凭证（级联吊销访问凭证，且注册凭证被吊销后无法再换发）。
- 同一时刻每个注册凭证只有一个有效的访问 secret。这与 [ADR-0009](0009-credential-bound-backend-identity.md)（一张凭证即一个后端）和 [ADR-0010](0010-replaced-backend-stands-down.md)（被顶替方退出）一致：另一进程换发会让本进程缓存的 secret 失效，SDK 在下一次握手被拒（`UNAUTHORIZED`）时会在同一次尝试内重新换发。已建立的连接不会因轮换被断开（网关不对在线连接重新校验 token，与过期的处理相同）。
- 约束落在数据库：`credentials(parent_id)` 上对 `type = 'backend-access'` 的部分唯一索引。升级时先折叠存量重复行——每个注册凭证保留一行（优先未吊销、其次最新），其余删除；被删的 token 若仍有 SDK 在用，下次握手被拒后自动重新换发。
- 审计：`credential.exchanged` 语义不变（每次换发一条），新增字段 `rotated=true|false` 标明是否为原地轮换。原先"换发时清理过期行"的方案随之取消。

## 后果

- 正面：管理列表中每个后端恰好一行访问凭证，不随重启与重连增长；无需任何清理逻辑；凭证 id 稳定。
- 负面/需要承担的：失去按单张 token 的审计粒度（`lastUsedAt`、吊销都落在同一行；历史只能从审计日志追溯）；无法让同一注册凭证同时持有两个有效的访问 secret；被单独吊销的访问凭证会在下次换发时恢复为有效（以新 secret）。
- 触发重新评估的条件：出现同一逻辑后端多实例同时在线（多活）的需求——届时每个实例需要各自的访问凭证，与 ADR-0009/0010 一同重新设计。
